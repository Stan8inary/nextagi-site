# AppoSight Chatbot — Project README

An on-site AI assistant for **apposight.com**. Visitors ask questions in a
floating chat bubble; the assistant answers strictly from what is published on
the site (the 12 public pages) plus live security briefings, grounded via
deterministic lexical retrieval and a Gemini model call. It runs as a Cloudflare
Worker paired with the main site Worker.

## What it is, in one paragraph

Two Cloudflare Workers in one account and one zone (`apposight.com`):

- **`www`** — the main site Worker. Serves all 12 public pages, the contact
  form (`/api/contact` → Brevo), the briefings API (`/api/briefings*`), and the
  admin page. Owns the `CONTACT_FORMS`, `RATE_LIMIT`, and `BRIEFINGS` KV
  namespaces.
- **`apposight-chat`** — the chat Worker (this project). Serves the client
  widget and the `/api/chat` SSE endpoint, routed at
  `apposight.com/api/chat*` and `www.apposight.com/api/chat*`. Owns the `KV_LOG`
  namespace and the `Limiter` Durable Object, and **reads** the shared
  `BRIEFINGS` namespace (read-only).

Both share the `BRIEFINGS` KV namespace (the chat Worker is a **read-only**
consumer of it — it never writes to `BRIEFINGS`).

```
   │  ├─ knowledge.js          # AUTO-GENERATED by build_knowledge.js (DO NOT EDIT)
   │  └─ widget.js             # AUTO-GENERATED from chat-widget.js (DO NOT EDIT)
   ├─ chat-widget.js           # the REAL client widget source (edit THIS)
   ├─ build_knowledge.js       # regenerates src/knowledge.js + src/widget.js
   ├─ tests.js                 # chat-worker test suite (156 tests)
   ├─ test-cf-hook.mjs         # test loader hook (import for node)
   ├─ wrangler.toml
   ├─ .dev.vars                # DEV-ONLY local keys (git-ignored; never committed)
   ├─ DEPLOY-RUNBOOK.md        # full production deploy/rollback runbook

```

**Do not hand-edit** `src/knowledge.js` or `src/widget.js` — they are
generated. Regenerate them with `node build_knowledge.js` (see OPERATIONS.md).

## Quick start (local, no prod impact)

All commands run from `public_html/chat-worker`.

```bash
cd /home/nextagi/public_html/chat-worker

# 1. Regenerate the knowledge base + widget bundle from the current
#    main-worker pages and chat-widget.js (idempotent, read-only on worker/):
node build_knowledge.js

# 2. Run the full test suite (deterministic, no network, no model):
node --import ./test-cf-hook.mjs tests.js
#    expected: "RESULT: 156 passed, 0 failed"

# 3. (Optional) local end-to-end smoke with a DEV origin + always-pass Turnstile
#    (uses .dev.vars; the /dev harness page is served ONLY when DEV_ORIGIN is set):
npx wrangler dev
#    open http://localhost:8787/dev   → chat bubble boots, send a message
```

`wrangler dev` injects `.dev.vars` (local test keys) and `DEV_ORIGIN`, so the
dev harness + an in-memory limiter fallback become available. **None of this
touches production** — production reads its vars/secrets from the Cloudflare
environment, never from `.dev.vars`.

## Ground rules (carry into every change)

- **Preview before publish, verify live after.** Never deploy un-previewed.
- **Never print or store secrets** (API keys, tokens, passwords, customer data).
  References in docs are **by name only**.
- **Commit by file name only**, staging exactly the files you changed.
- The chat Worker's `BRIEFINGS` binding is **read-only**; a test enforces that
  no `BRIEFINGS.put`/`.delete` exists in the chat Worker.
