# AppoSight Chatbot — Architecture

Two Cloudflare Workers in one account, one zone (`apposight.com`). The chat
Worker (this project, `apposight-chat`) answers visitor questions from the site
content and live briefings; the main Worker (`www`) serves the site, the contact
form, the briefings API, and the admin page.

## The two Workers

| Worker | name | Serves | Owns (writes) | Reads |
|---|---|---|---|---|
| Main site | `www` | 12 public pages, `/api/contact`, `/api/briefings*`, `/admin` | `CONTACT_FORMS`, `RATE_LIMIT`, `BRIEFINGS` KV | — |
| Chat (this) | `apposight-chat` | `chat-widget.js`, `/api/chat` (SSE) | `KV_LOG` KV, `Limiter` DO | `BRIEFINGS` KV (**read-only**) |

They share the **`BRIEFINGS`** KV namespace. The chat Worker is a strict
read-only consumer: a test in `tests.js` fails the suite if any `BRIEFINGS.put`
/ `delete` / list-write appears in chat-worker source.

Chat routes (from `wrangler.toml`): `apposight.com/api/chat*` and
`www.apposight.com/api/chat*`. The main Worker owns everything else.

## Request flow (ASCII)

```
                       browser (any public page)
                       chat-widget.js  (fetched from /api/chat-widget.js)
                            |
                            |  POST /api/chat   { messages[], cf_turnstile_response }
                            v
        +---------------------------------------------------------------+
        |  Worker: apposight-chat  (src/index.js, /api/chat)            |
        |                                                               |
        |  1. parse + size checks        (body 20000B cap -> 413)       |
        |  2. per-message caps           (500-char user msgs -> 400)    |
        |  3. trim history               (assistant->700c, keep 2, 6000c)|
        |  4. per-IP limiter (DO)       (20/min  -> 429 rate_limited_ip)|
        |  5. Turnstile verify          (invalid->403; expired->retry x1)|
        |  6. daily limiter (DO/KV)     (300/day -> 429 daily_cap)      |
        |  7. EARLY SSE 'status' event  (FIRST BYTES, before model/KV)   |
        |                                                               |
        |  8. briefing intent?                                               |
        |     yes -> read BRIEFINGS KV (read-only) -> grounded answer  |
        |     no  -> retrieval over knowledge.json (IDF chunks)         |
        |              (social/brand/listing/canned modes)             |
        |                                                               |
        |  9. Gemini call (streaming SSE)                              |
        |     gemini-3.5-flash-lite, thinkingLevel MINIMAL             |
        |     TTFB 8s; retry ONCE on timeout/5xx-before-bytes          |
        |     relay: idle 15s, overall cap 45s                         |
        |                                                               |
        | 10. log: q_ (question, 30d) + t_ (timing, 7d) + m_ (issue)    |
        +---------------------------------------------------------------+
                            |
                            |  SSE: status -> delta* -> done  (or error)
                            v
                       browser: widget renders answer, links, source chips
```

## Module map (chat-worker)

| File | Responsibility | Notes |
|---|---|---|
| `src/index.js` | fetch handler, `/api/chat`, SSE relay, all orchestration, logging | the "glue"; holds every constant below |
| `src/retrieval.js` | deterministic lexical/IDF chunk scoring, pure | no I/O; unit-testable |
| `src/briefings.js` | briefing intent detection + KV reads, pure | read-only |
| `src/limiter.js` | `ChatLimiter` Durable Object (per-IP minute + daily cap) | sqlite-backed DO |
| `src/text.js` | `stripInlineRefs` / `safePrefix` (pure) | strips model's inline refs before send |
| `src/knowledge.js` | **AUTO-GENERATED** chunked site content | generated by `build_knowledge.js` |
| `src/widget.js` | **AUTO-GENERATED** widget bundle | generated from `chat-widget.js` |
| `chat-widget.js` | the real client widget source (edit THIS) | — |
| `build_knowledge.js` | regenerates `knowledge.js` + `widget.js` | idempotent, read-only on `worker/` |
| `tests.js` | 156-test suite | run with `node --import ./test-cf-hook.mjs tests.js` |

## KV log policy & key prefixes

All writes are fire-and-forget via `waitUntil` (never block the response).
Three prefixes, three TTLs:

| Prefix | Content | TTL | Never logged |
|---|---|---|---|
| `q_` | question text (the user's last message) | `30 d` | IPs, emails, model API key |
| `t_` | per-request timing (stage, ms, attempt, outcome) | `7 d` | question text |
| `m_` | a single "model issue" record (error code, reason) | `30 d` | the Turnstile token, upstream bodies |

Design rules enforced by code + tests:
- **Fail-closed limiter** — in production (no `DEV_ORIGIN`), the Durable Object
  is the only limiter; if it is unavailable the request is rejected `503` rather
  than falling back to a per-process counter (which could under-count the global
  cap across isolates).
- **No PII in logs** — `m_` records the Turnstile `error_code` only, never the
  token; `t_` records stage + timing only, never the question.
- **KV write failures are counted, not fatal** — the chat still answers (or
  returns its classified error); the failure is logged with an isolate-local
  counter (`kvWriteFailures`).

## Model call (Gemini)

- Streaming SSE from the Gemini generateContent endpoint.
- `generationConfig.thinkingConfig`:
  - gemini-3.x → `thinkingLevel` (default `MINIMAL`).
  - gemini-2.5.x → `thinkingBudget` (numeric; `''`/unset → model default).
- **Never captures or propagates the upstream response body** on error (404/403)
  — only the status code is recorded.
- Retry policy: at most **2 attempts**; a retry is allowed **only** on attempt 1
  and **only** for a timeout or a 5xx seen before any byte. The final failure
  writes exactly one `m_` log + one `t_` outcome + an SSE `error` event.
- `[[LEAD_CAPTURE]]` marker: the model may emit it to signal a lead; the relay
  strips it from the stream before it reaches the browser.

## SSE event contract (worker → widget)

| Event | Payload | Meaning |
|---|---|---|
| `status` | `{ok:true, phase:"working"}` | FIRST BYTES — sent before any KV/model work |
| `delta` | `{text}` | incremental answer text (safe-prefixed, refs stripped) |
| `done` | sources / lead-capture metadata | stream complete |
| `error` | classified error (e.g. `model_404`, timeout, 5xx) | stream aborted with reason |

Stage markers (for `wrangler tail` debugging): `request_received`, `body_ok`,
`limiter_ok`, `turnstile_ok`, `first_byte`, `briefing_resolved`,
`retrieval_done`, `model_start`, `stream_done`, plus `stageErr` names on failure.

## Retrieval (deterministic, no LLM)

`retrieval.js` scores knowledge chunks against the query using IDF-weighted
lexical matching over the chunked site content in `knowledge.js`. Modes selected
by intent:
- **briefing** — reads `BRIEFINGS` KV (read-only), date-grounded answer.
- **social / brand / listing** — intent-specific system prompts (e.g. brand
  service areas, "where do you work" listings that include home/about).
- **canned** — fixed "I don't have that on the site" reply when nothing matches.

Retrieval output feeds the system prompt; the model then produces a grounded,
cited answer with source chips.
